## Commands

```bash
pnpm install          # first-time setup
pnpm dev              # next dev — http://localhost:3000
pnpm build            # production build
pnpm start            # serve the production build
pnpm lint             # next lint (uses Next.js defaults)
pnpm type-check       # tsc --noEmit
```

There is no unit-test runner in this project. The pure modules that warrant checking are
exercised by scripted assertion files:


## Auth gotchas

- **The `sat` schema MUST be exposed in Supabase API settings.** The app queries `sat.profiles` via `supabase.schema('sat').from('profiles')` (PostgREST). Supabase only exposes the `public` schema by default. If `sat` is not added to Settings → API → Exposed Schemas, every call to `getOrCreateProfile()` fails — every authenticated page will error. This is a one-time dashboard action on the Property Ledger project (`falgykkspbtrwdcchayi`).

- **`sat.profiles.role` is not user-writable — enforced by a trigger.** The migration uses column-scoped `GRANT`s, but Supabase re-grants table-level `INSERT`/`UPDATE` to `anon`/`authenticated` on tables in exposed schemas (its "grant broad, secure with RLS" model), and RLS only restricts *which rows* a user touches — not *which columns*. So the real guard is the `profiles_protect_role` BEFORE INSERT OR UPDATE trigger (`sat.protect_profile_role()`): for API roles (`anon`/`authenticated`) it forces `role` to `'student'` on insert and silently keeps the existing `role` on update — a user cannot escalate to `admin` via the API. Privileged roles (`postgres`/`service_role`) are unaffected. To promote a user to admin, run a direct `UPDATE` as the `postgres`/service role: `update sat.profiles set role = 'admin' where id = '<user-uuid>';` **If you add another privileged column to `sat.profiles`, extend that trigger.**

- **Profile rows are created by `getOrCreateProfile()`, NOT by a database trigger on `auth.users`.** The Property Ledger Supabase project is shared with the PropLedger app. An `on_auth_user_created` trigger on the shared `auth.users` table would fire for every PropLedger sign-up, creating junk `sat.profiles` rows. Application-code provisioning keeps the SAT app fully confined to the `sat` schema. `getOrCreateProfile()` is called on every authenticated entry point (`AppHeader`, `(app)/page.tsx`, `(app)/dashboard/page.tsx`), so the row is reliably created on first load regardless of sign-up method.

- **Middleware gates everything except `PUBLIC_PATHS`.** The public paths are: `/login`, `/register`, `/forgot-password`, `/reset-password`, `/auth/callback`. Every other route requires a session — `middleware.ts` redirects unauthenticated requests to `/login`. If you add a new public route (e.g. a health-check endpoint), add it to `PUBLIC_PATHS` in `middleware.ts` or it will be gated.

## AI sub-project gotchas

- **`app/lib/supabase/admin.ts` is server-only.** It imports `SUPABASE_SERVICE_ROLE_KEY` (never `NEXT_PUBLIC_`-prefixed). If you import `createAdminClient` into any `'use client'` module, Next.js will bundle the service-role key into the browser bundle — a critical secret leak. Only import it from route handlers, server actions, or other server-only files (`generate.ts`, `seed-questions.ts`). Verification command (run from the project root):
  ```powershell
  Get-ChildItem -Path app -Recurse -Include *.tsx,*.ts | Select-String -Pattern "supabase/admin|SUPABASE_SERVICE_ROLE_KEY"
  ```
  Expected: matches only in `app/lib/supabase/admin.ts`, `app/lib/ai/generate.ts`, `app/lib/persistence/failures.ts` (the shared `logSaveFailure` diagnostics writer — writes the `sat.save_failures` row for both attempt and practice saves), `app/lib/practice/generation.ts` (the Dynamic Practice service-role writer — see the Dynamic Practice sub-project gotchas), and the four admin service-role modules `app/lib/admin/actions.ts`, `app/lib/admin/flags.ts`, `app/lib/admin/queries.ts`, `app/lib/admin/users.ts` — eight files total, all server-only modules, never a `'use client'` module.

- **`sat.questions` has only a `select` RLS policy — users cannot write to it.** The migration deliberately omits an insert/update/delete policy. Authenticated users can read the pool (for the RPC), but any direct write via the anon/authenticated role is denied by RLS. New questions are written exclusively by the generation endpoint via the service-role client (which bypasses RLS). The seed script likewise uses the service-role client.

- **`service_role` needed an explicit `USAGE` grant on the `sat` schema.** Foundation's `20260521000000_sat_schema.sql` granted `USAGE` on `sat` only to `anon` and `authenticated`. The service role's `BYPASSRLS` attribute bypasses row-level security but does NOT grant schema-level privileges — the service role was still blocked from writing `sat.questions`. Migration `20260521040000_sat_service_role_grants.sql` adds `GRANT USAGE ON SCHEMA sat TO service_role` plus full table/sequence privileges. If you add new tables to the `sat` schema that the service role must write, confirm the grants or re-run this migration.

- **`/api/admin/generate-questions` is in `PUBLIC_PATHS` but is secret-gated.** The route is excluded from the session middleware (it has no user session — it is called by Vercel Cron). It authenticates itself with `Authorization: Bearer <CRON_SECRET>` instead. A request without that header returns `401`. Do not add session gating to this route; do not remove it from `PUBLIC_PATHS`.

- **AI-generated explanations are rendered React-escaped — not via `dangerouslySetInnerHTML`.** `ReviewItem.tsx` branches on `question.source`: `'seed'` explanations use `dangerouslySetInnerHTML` (trusted, hand-authored, may contain `<b>` tags); all other sources (i.e. `'ai'`) render via `<span>{question.explanation}</span>` — React escapes the content. The Ollama prompt asks for plain-text explanations, so no formatting is lost. Do not widen `dangerouslySetInnerHTML` to AI-sourced questions.

- **`BANK` is now the seed source and offline fallback only.** The runtime question source is `sat.questions` (via the `draw_questions` RPC in `app/lib/pool.ts`). `useTestSession.start()` is async: it draws from the pool and falls back to `BANK` only if the draw throws or returns empty. Adding questions to `BANK` without re-running the seed script will not make them visible to users at runtime; update `sat.questions` directly, or extend the seed and re-run it.
- **Explanations must not reference choices by letter or number.** Because `buildTest()` shuffles choices per test, an explanation that says "Choice A is correct because..." becomes wrong at runtime if A is no longer the correct slot — the displayed "Correct answer: B" then disagrees with the explanation's text. The `ollama.ts` prompt forbids it, the n8n Plan Batches prompt forbids it, and the n8n Parse Candidates node has a `repairLetterRefs()` regex pass that rewrites surviving "Choice X" / "Option N" references before insert (correct-index → "the correct choice", incorrect-index → "another choice"). Don't add a feature that reintroduces letter references — write them as "the correct choice" or quote the option's content instead.
- **The generator buffer is per-user, not global.** The gate calls `sat.min_active_user_unseen()` (security-definer, aggregates across users) and only generates while the worst-off active student's unseen count is below `BUFFER_TARGET`. The old global gate (count of questions never served to *anybody*) over-fired the generator: a question served only to the most-prep-active student counted as "used" even though every other student still had it ahead of them. Active = ≥ 1 saved test attempt — pure account-only sign-ups don't influence the gate. If you change attempt-counting semantics, revisit the RPC.
- **There is a SECOND gate: the per-skill floor.** Generation also fires when any `(section, skill)` slot has fewer than `SKILL_FLOOR` (3) enabled questions, regardless of the per-user buffer state. This auto-populates newly added skills without a manual backfill — add a name to `SKILLS` in `app/lib/questions.ts`, and the n8n workflow's thinnest-first picker fills that slot within ~5 hourly ticks. Once every slot is at the floor AND the buffer is healthy, the generator returns to no-op. The dual gate is enforced in BOTH `generate.ts` (Vercel cron path) and the n8n workflow's Plan Batches node — keep them in sync.
- **The `SKILLS` taxonomy lives in two places.** Source of truth is [app/lib/questions.ts](app/lib/questions.ts); a duplicate hardcoded copy lives in the n8n Plan Batches node `jsCode`. Update both in the same change — drift breaks the generator's skill-pin check (the n8n workflow would request generation for a skill name the app doesn't know, and the test runner's analytics wouldn't surface it). Future cleanup: dedupe via a `sat.skills_taxonomy()` RPC; deferred. The CLAUDE.md gotcha lives here as a reminder. **Third place, for Practice:** adding a skill to `SKILLS` also fails `scripts/check-lessons.ts` until a matching static lesson exists in `app/lib/lessons/` (see the Practice sub-project gotchas) — author the lesson in the same change.
- **Cloze passages must contain `______` (six underscores); RC passages must not.** Completion-style skills (Boundaries, Form & Structure (Verbs), Pronoun/SV Agreement, Transitions, Words in Context) require a `______` marker at the insertion point. RC skills (Central Ideas, Command of Evidence) must be complete prose with no blank. The n8n Parse Candidates node enforces both directions: if a completion passage is missing the blank, `repairMissingBlank()` finds the correct choice's text inside the passage and replaces it with `______`; if an RC passage has a blank, `repairRcBlank()` replaces it with the correct choice's content. Candidates that can't be repaired are dropped.
- **n8n primary uses 3 different models for a vote pattern.** The ACT Config Provider workflow (`ghVKwVwYjB7T2vPY`) exposes `ollamaGenerateModel` (DeepSeek), `ollamaSolveModel` (Gemini, cross-provider), and `ollamaTiebreakModel` (Gemma). The main generator workflow (`TTq4YrS1c1qqdUmt`) uses generator-then-solver-then-tiebreak: the solver re-solves with a different model; if it disagrees with the generator, the tiebreaker votes; 2-of-3 majority wins or the candidate is dropped. Cross-provider diversity means the 3 models have independent blind spots — this catches more bugs than 3 calls to the same model. The SAT side (`kFGnGakMnPQH4nNj` Config Provider + `jDjJIthvf6EyKwgR` generator) uses the same 3-slot pattern. **The Vercel cron path (`app/lib/ai/generate.ts`) stays single-model on purpose** — it's the cheap backup; quality work happens in n8n.

## Format Parity (SPR) sub-project gotchas

The format-parity sub-project has landed: Math questions can now be **student-produced-response (SPR / grid-in)** in addition to multiple-choice, matching the ~25% SPR share on the real Digital SAT Math section. R&W stays mcq-only. A Desmos scientific calculator and a Math reference sheet are available during Math sections.

- **`response_format` is the discriminator end-to-end.** It lives on `sat.questions` (`'mcq' | 'spr'`, default `'mcq'`), on `sat.attempt_responses` (snapshotted at save time), in the zod `generatedQuestionSchema` (`z.discriminatedUnion('responseFormat', [...])`), in `SolveInput`/`SolveResult`, in the `Question` interface, and in `ResponseValue` (`number | string | null`). Every branch in the pipeline (generator → solve → insert → draw → render → save → review) keys off this column. **Never add a third format without extending every branch — including the n8n Plan Batches, Parse Candidates, Check Answer, and Tiebreak Decide nodes.**
- **SPR canonical answer is server-trusted; the client never sees it during a test.** `correct_answer` and `answer_tolerance` are columns on `sat.questions`, drawn into the in-memory `Question` for *review only* (the runner does not display them while answering). The runner sends `entered_value` (a string) to `sat.save_attempt`, which **re-joins to `sat.questions` by `question_id` and computes `is_correct` server-side** via `sat.spr_is_correct`. A client that lies about the canonical answer in its payload is silently ignored. This is the SPR analogue of the mcq-shuffle-snapshot pattern — but inverted: mcq snapshots the *as-presented* shuffled choices+answer_index because there is no client-tamper risk (the index is just a position), whereas SPR's canonical lives on `sat.questions` (untrusted by client). Do not "simplify" `save_attempt` by trusting the client-provided correct_answer; keep the join.
- **SPR rows in `attempt_responses` keep mcq columns as placeholders, not nulls.** `chosen_index` is set to a sentinel (the row also writes `entered_value = '<typed>'`) and `choices` is left as the empty array snapshotted from the question. The mutual-exclusion rule is read at the row level: `response_format = 'spr'` means use `entered_value` + `correct_answer`; `response_format = 'mcq'` means use `chosen_index` + `choices[answer_index]`. The review UI (`ReviewItem`) branches on `response_format` accordingly — do not branch on which column happens to be null.
- **The JS parser and the Postgres helper MUST stay byte-for-byte equivalent.** `app/lib/spr.ts` (`parseSpr` / `isSprCorrect`) mirrors `sat.spr_to_numeric` / `sat.spr_is_correct`. The runner gives instant feedback against the JS parser; the RPC is the airtight backstop. If the two disagreed, a client could pass a string the JS parser accepts but Postgres rejects (or vice versa) and see different correctness on screen vs. in the saved attempt. Whenever you touch one, update the other AND re-run `scripts/check-spr.ts` (37 assertions cover acceptance, rejection, equivalent forms, tolerance, inequality).
- **`isSprCorrect` does exact-string compare first, numeric compare second.** Exact-string is the canonical SAT rule for fractions (e.g. canonical `"3/4"` and entered `"3/4"` agree even if numeric compare would round). Numeric compare follows for cases like `0.5` vs `1/2`. Mixed numbers (`"1 1/2"`) are rejected at parse time — the real SAT forbids them. If you change comparison semantics, change both layers and the script.
- **Calculator + reference are Math-only and Math-only state-wise.** `TestScreen` reads `isMath = section.key === 'math'` and *only renders the toolbar buttons + state when true*. Section transition unmounts the panels automatically (`useState` is scoped to the current section render). Do not lift this state up to `useTestSession` — keeping it in `TestScreen` is what makes section-change auto-close work without explicit cleanup. The Desmos embed is scientific, not graphing; upgrade by swapping the iframe src in [app/components/CalculatorPanel.tsx](app/components/CalculatorPanel.tsx).
- **SPR generation is a per-target coin flip, not a quota.** `generate.ts` computes `useSpr = section === 'math' && Math.random() < SPR_PROBABILITY (0.25)` *inside the targets loop* — over time the pool's Math rows trend toward ~25% SPR, but a single run is all-or-nothing for that target's batch. The n8n Plan Batches node does the same coin flip; the two are independent, so the realized share converges by law-of-large-numbers, not by a shared counter. Do not "fix" this with a deterministic counter unless you intentionally want to tighten the variance.
- **SPR dedup hash uses `[correctAnswer]` as the choices argument.** `dedupHash` normalises and hashes `(prompt, choices, passage)`. SPR rows have no choices, so calling `dedupHash(prompt, [], null)` would collapse every SPR question to one prompt-only hash (and a UNIQUE-constraint storm). Passing `[q.correctAnswer]` as the second arg is the convention that lets two SPR questions with the same prompt but different canonical answers coexist (rare but possible: "What is x?" with different equations preceding the same final sentence). Keep the convention; do not switch to `(prompt only)` hashing for SPR.

## Persistence sub-project gotchas

- **`sat.test_attempts` and `sat.attempt_responses` are RLS select-only.** Each table has a `select` policy scoped to `auth.uid()` and *no* insert/update/delete policy — even though Supabase grants table privileges to `authenticated` on exposed-schema tables, RLS with no write policy denies all writes. The only writer is the `sat.save_attempt` security-definer RPC, which bypasses RLS and sets `user_id := auth.uid()` itself. This mirrors the `sat.questions` / `draw_questions` pattern. If you add a write path, go through a security-definer function — do not add a write policy.

- **`attempt_responses` rows snapshot the question as it was presented.** Each row stores the per-test-shuffled `choices`, the remapped `answer_index`, and the `explanation` — not a reference to the live `sat.questions` row. `buildTest()` shuffles each question's choices per test, so a stored `chosen_index` is meaningless against the original question's choice order. The review page (`/dashboard/attempts/[id]`) must read these snapshotted columns; never re-join to `sat.questions` to "freshen" a past attempt. **Exception:** for `response_format = 'spr'`, `correct_answer` and `answer_tolerance` are snapshotted alongside `entered_value` — see the Format Parity gotchas for why the canonical comes from the server (`save_attempt` joins to `sat.questions`) rather than the client.

- **The wire `attemptResponseSchema` must accept SPR (grid-in) responses — `choices` is per-format, not flat-`.min(1)`.** Bug (2026-06-12, found via `sat.save_failures`): once the pool gained SPR questions, every test that drew a grid-in failed to save with `invalid_payload` — `attemptResponseSchema.choices` was `z.array(z.string()).min(1)`, but SPR rows carry `choices: []`, so the whole payload was rejected before reaching the RPC and the attempt was lost (and `invalid_payload` is a TERMINAL error, so retry/backup couldn't recover it on the old client). The schema must (1) allow empty `choices` and enforce non-empty only for mcq via a `.refine(r => r.responseFormat === 'spr' || r.choices.length >= 1)`, and (2) **list the SPR fields** (`responseFormat`, `enteredValue`, `correctAnswer`, `answerTolerance`) so zod's strip mode doesn't drop them — `sat.save_attempt` reads `responseFormat` + `enteredValue` off the payload. `scripts/check-payload.ts` guards both directions (SPR with `[]` passes; mcq with `[]` rejected). If you add a wire field consumed by the RPC, list it in the schema or it is silently stripped.

- **`toAttemptPayload` is checked by a script, not a test runner.** The project still has no unit-test runner. `toAttemptPayload` (the pure mapper in `app/lib/persistence/payload.ts`) is exercised by `scripts/check-payload.ts`, run with `tsx` (`pnpm dlx tsx scripts/check-payload.ts`). If you change the payload shape, update that script too — it is the only automated check on this mapper.

- **The save path is retry-backed + locally-backed-up — it used to be one-shot and lossy.** The original bug ("Couldn't save this attempt — your history may be incomplete"): the save was a single fire-and-forget call of an in-memory-only attempt, with `savedRef` set BEFORE the call (blocking re-fire), no retry, and no "Retry save" button — so ANY transient failure (mobile blip, serverless cold-start, token-refresh race) permanently destroyed a finished test, and the real error was only `console.error`'d in the browser. The hardened path: (1) on results-screen entry, `toAttemptPayload` is written to localStorage (`sat:pending-attempt:v1`) via `app/lib/persistence/backup.ts` BEFORE the network call; (2) `runSave` in `useTestSession` calls `saveAttempt` through `withRetry` (`app/lib/persistence/retry.ts` — exponential backoff + jitter, retries transient failures, stops on terminal ones: invalid payload / daily limit / no responses / not authenticated); (3) on success the backup is cleared, on final failure it stays and a "Retry save" button + the real error string are shown; (4) a mount effect auto-resaves any leftover backup (survives tab close / reload), guarded by `resaveStartedRef` against Strict-Mode double-fire. Pure logic is covered by `scripts/check-retry.ts` and `scripts/check-backup.ts`. **Idempotency (closed, migration `20260531010000`):** the client generates one `attemptUuid` per finished test (carried in the backup, every retry, and the resave). `save_attempt` short-circuits on it — `sat.test_attempts.attempt_uuid` + a partial unique index `(user_id, attempt_uuid)`; a repeat returns the existing id **before** the daily-limit check (so a resave is never charged a limit slot) and a concurrent same-uuid race is resolved in the `unique_violation` handler. So a lost-success-response resave is a no-op, not a duplicate. The action passes `attemptUuid` via `p_attempt.attemptUuid`; a null/absent key falls back to always-insert (older clients). When changing `save_attempt`, preserve the early short-circuit ordering AND the exception handler.

- **`sat.save_failures` is the diagnostic trail for failed saves (migration `20260531000000`).** Every failed `saveAttempt` writes a best-effort row (error message, coarse `error_code`, `retryable`, `attempt_no`, and a `context` jsonb with testLength/totalQuestions/attemptUuid/userAgent) via the **service-role** client — so it records even the "not authenticated" failure mode where the caller has no session. RLS-on, policy-less (only the service role touches it, same posture as `question_flags`). Query it to confirm the real-world failure trigger: `select error_code, count(*) from sat.save_failures group by 1`. Logging never throws — a logging failure must not mask the user's real error.

- **Full-test pause ("Allow breaks") is a per-session flag, not a test type (migration `20260531020000`).** `useTestSession` holds `breaksEnabled` (start-screen toggle, default OFF, force-set `false` for short tests in `start()`), `paused`, and `breaksUsed` (sticky — set on first `pause()`, reset only by `start()`/`newTest()`). **Pausing freezes the clock by adding `paused` to the countdown effect's guard + deps** — that interval is the sole mutator of `remaining[][]`, so suspending it freezes time with no separate accounting; `pause()` must NOT call `stopTimer()` (the effect's `return stopTimer` cleanup does). The `PausedOverlay` is `fixed inset-0 z-50` near-opaque so a break can't be used to keep reading (it auto-focuses Resume + Escape resumes, so keyboard users can't Tab to the hidden question either). The Pause button + toggle render only for full tests with `breaksEnabled`. `breaks_used` threads payload → `save_attempt` → `test_attempts` and is surfaced as a "with breaks" tag on results/dashboard/review — **informational only; it MUST NOT be read by `sat.scale_section` or any scoring path** (same discipline as "scaled_score is server-trusted"). In-session only: closing the tab mid-test still loses the attempt.

State lives entirely in URL query params — [app/lib/admin/users-search.ts](app/lib/admin/users-search.ts) is the single source of truth for the param shape, defaults, and URL helpers; the toolbar ([app/components/admin/UsersToolbar.tsx](app/components/admin/UsersToolbar.tsx)) calls `router.replace(buildUsersHref(...))` on every change with a 250ms debounce on the text search. `pg_trgm` is enabled and GIN-indexes back the substring search on `lower(full_name)` / `lower(email)`. **Do not add a write path through these RPCs** — they are read-only by design; promote/demote needs its own server action behind `requireAdmin()` plus a `profiles_protect_role` trigger change (deferred, see the auth gotchas).
- **PL/pgSQL functions that `RETURNS TABLE(...)` need `#variable_conflict use_column`.** Every column declared in the `RETURNS TABLE` clause becomes an implicit OUT variable visible throughout the function body. Any unqualified column reference whose name happens to match one of those OUT vars raises `42702: column reference X is ambiguous` at *call time* (not create time — PL/pgSQL plans lazily). This bit `admin_users_search` v1 (the `role` OUT var collided with `sat.profiles.role` in the caller-role lookup; the `created_at` OUT var collided with `max(created_at)` inside an aggregate subquery). The function looked fine until a real admin called it; the supabase-js client received the error, the wrapper fell back to empty rows, and the page rendered "No users yet" while the headline stats (no colliding OUT names) reported the real total. Fix: add `#variable_conflict use_column` immediately after `as $$` and qualify your `select INTO` source tables. Apply this to any future security-definer RPC that returns a typed table whose column names overlap with source-table columns (which is most of them).

## Practice sub-project gotchas

The practice sub-project has landed (sub-project #13): `/practice` is a focus-area hub, and `/practice/[skill]` pairs a static lesson with an untimed, instant-feedback skill **drill** drawn from the live `sat.questions` pool. It turns analytics weak spots into targeted reps without touching test-based score validity.

- **`sat.practice_sessions` / `sat.practice_responses` are RLS select-only — the only writer is `sat.save_practice`.** Each table has a `select` policy scoped to `auth.uid()` and *no* insert/update/delete policy (same posture as `sat.test_attempts` / `sat.attempt_responses`). Writes go exclusively through the `sat.save_practice(p_session, p_responses)` **security-definer** RPC, which sets `user_id := auth.uid()` itself. It is **idempotent on `(user_id, session_uuid)`**: the existence short-circuit runs BEFORE any insert (returns the existing session id), and a concurrent same-uuid race is caught in a `unique_violation` handler — the same discipline as `save_attempt`'s `attempt_uuid`. **Correctness is recomputed server-side, never trusted from the client:** mcq from the snapshotted `chosenIndex` vs `answerIndex`; SPR by re-joining `sat.questions` by `question_id` for the canonical `correct_answer`/`answer_tolerance` and running `sat.spr_is_correct`. The client-sent `isCorrect` is display-only (instant feedback in the drill) and is ignored at save. If you add a practice write path, go through a security-definer RPC; do not add a write policy.
- **`sat.draw_drill(p_skill, p_count)` is missed-first, and it UPSERTS `served_questions` for everything it returns.** Tier 1 = **currently-missed** questions — a question qualifies when the user's *latest* recorded answer across BOTH `sat.attempt_responses` and `sat.practice_responses` (whichever is most recent by `answered_at`) was wrong — capped at `ceil(count/2)` and ordered most-recent-miss first. Tier 2 = **fresh** (never in `served_questions` for this user). Tier 3 = **recycled** (least-recently-served). Because every returned id is upserted into `sat.served_questions`, drilled questions are marked as served and **never later appear on a test as "unseen"** — the demand-driven generator (`sat.min_active_user_unseen()` per-user buffer gate) absorbs the resulting buffer drain by generating more, so drilling silently increases pool demand. **The return order is meaningful (missed first); the client must NOT shuffle the question array** — only per-mcq choices get shuffled, via `shuffleChoices` (a no-op for SPR). `drawDrill` in `app/lib/practice/draw.ts` documents this.
- **Practice results deliberately do NOT feed `/analytics`.** Mastery tiers and focus areas are driven by *test* accuracy only, to preserve score validity (a drill is not a proctored, timed measurement). The Practice hub surfaces practice progress **separately** via `sat.practice_skill_stats()` — a `security INVOKER` read-only aggregate (the `user_analytics` precedent: it reads only RLS-scoped tables, keeps an explicit `auth.uid()` filter as a clarity backstop, and must NOT be turned into a definer). `app/lib/practice/queries.ts` is the only surface that reads the practice tables; do not wire practice correctness into `getAnalytics()` or the mastery computation.
- **Lessons are static in-code content, enforced complete by `scripts/check-lessons.ts`.** One file per domain under `app/lib/lessons/` (8 domain files + `index.ts` registry `LESSONS` / `getLesson`), plain strings only (rendered React-escaped — no HTML, no letter references). `check-lessons.ts` asserts every skill in `SKILLS` (both sections) has a matching lesson with in-bounds fields and a valid worked example, plus slug round-trip/uniqueness. **Adding a name to `SKILLS` in `app/lib/questions.ts` fails that script until a lesson exists** — so a new skill is a three-place change (see the `SKILLS` taxonomy gotcha in the AI section: `questions.ts`, the n8n Plan Batches copy, and now a lesson).
- **`logSaveFailure` moved to `app/lib/persistence/failures.ts` (shared by attempt + practice saves).** It was inlined in `persistence/actions.ts`; it is now a server-only module (imports `createAdminClient`, so it appears in the secret-leak scan's expected list — see the AI sub-project gotchas). Its signature is keyed on a caller-built `context` jsonb: attempt saves pass `{ testLength, totalQuestions, ... }`, practice saves pass `{ kind: 'practice', skill }`. It still writes the same `sat.save_failures` row shape via the service-role client and still never throws. Query `select context->>'kind', error_code, count(*) from sat.save_failures group by 1, 2` to split attempt vs practice failures.
- **Drills are untimed and have NO daily limit — by design.** The per-user daily cap (see "Daily test limit") stays test-only: `save_practice` does not check `sat.app_config.daily_attempt_limit`, and `usePracticeSession` has no timers. Practice is meant to be unlimited, low-stakes reps. Do not extend the daily limit to drills.

## Dynamic Practice sub-project gotchas

The dynamic-practice sub-project has landed (sub-project #14): the static lesson is now a **fallback**, upgraded by an AI base lesson (shared, cached per skill); each student gets a per-skill "Coach's update" that regenerates when their performance moves; a post-drill top-up quietly refills the pool for the skill they just drilled; and `draw_drill` weights difficulty by rolling accuracy. Migration `20260707020000_sat_dynamic_practice.sql`.

- **The three new tables have three DIFFERENT RLS postures — and NONE has a write policy.** `sat.skill_lessons` has a select policy for `authenticated` with `using (true)` — the content is **shared, not per-user** (one lesson per `skill`, the pk), so any signed-in student reads any lesson. `sat.skill_guidance` is **select-own** (`user_id = auth.uid()`) — coaching is private. `sat.practice_topups` is RLS-on and **policy-less** — the anon/authenticated role can neither read nor write it; it is a service-role-only rate-cap trail (same posture as `sat.question_flags` / `sat.save_failures`). No table has an insert/update/delete policy: the **only** writer to all three is `app/lib/practice/generation.ts` via the service-role client. If you add a write path, go through that server-only module — do not add a write policy.
- **Definer-vs-invoker split across the three new RPCs — same discipline as `user_analytics`.** `sat.unseen_count_for_skill(text)` is **security DEFINER** because it must count against `sat.served_questions` across the caller's rows and needs to escape the `served_select_own` RLS scoping to count accurately (it sets `user_id := auth.uid()` itself — the client never supplies it; mirrors the draw RPCs). `sat.skill_latest_response(text)` and `sat.skill_evidence(text,int)` are **security INVOKER** — they read only RLS-scoped tables, so RLS confines them to the caller (each keeps an explicit `user_id = auth.uid()` filter as a clarity backstop — do not "clean it up"). All three needed an **explicit `grant execute`** — the `sat` schema is deny-by-default for functions (`20260521000000` revokes execute from anon/authenticated/public via default privileges), so a new function with no grant gets "permission denied". A read-only function over RLS-protected tables should stay invoker; do not promote the two invoker RPCs to definer.
- **`draw_drill` v2 is adaptive, but only Tier 2 is difficulty-shaped.** Rolling accuracy over the **last 20 responses** (across both response tables, ordered by the **parent-row `created_at`** — neither response table stores a per-row answer timestamp) picks a band: `<50%` → easy-lean 50/35/15, `50–75%` or `<5` responses of history → balanced 25/50/25, `>75%` → hard-lean 10/35/55. The band's percentages are largest-remainder split into easy/med/hard sub-quotas over the **remaining** slots after Tier 1, and applied only to **Tier 2 (fresh)** (per-difficulty fill, then any-difficulty remainder). **Tier 1 (currently-missed) and Tier 3 (recycled) stay difficulty-agnostic BY DESIGN** — a student's actual misses are drilled regardless of difficulty, and recycling by `served_at` is level-blind on purpose. v2 is `CREATE OR REPLACE` with the same signature, which **PRESERVES the v1 ACLs** — no re-grant needed (do not add a `grant execute` for `draw_drill` "to be safe"; it is deliberately omitted). Preserved from v1: enabled-only, de-dup via `v_ids`, the `served_questions` upsert, and `array_position` return ordering (missed-first — the client must not shuffle).
- **Neither response table stores `difficulty` — it comes from a join to `sat.questions`, and in `skill_evidence` that join is LEFT so difficulty CAN be null.** `sat.attempt_responses` / `sat.practice_responses` snapshot the presented question but not its difficulty. `sat.skill_evidence` LEFT-joins `sat.questions` by `question_id` to recover it — LEFT because a response can outlive its question row (no FK back), so `difficulty` is nullable here even though `sat.questions.difficulty` is not-null. When it is null, the guidance prompt simply **omits the difficulty tag** for that evidence line (`difficulty` is passed through to `GuidanceEvidenceItem` as-is, possibly null). Do not "fix" this to an INNER join — you would silently drop evidence for any answered-then-deleted question.
- **`generateBatchForSkill` (`app/lib/ai/generate.ts`) is shared by the cron path AND the top-up route — the per-row `23505` catch is load-bearing.** It was extracted from `runGeneration`'s inner loop verbatim (SPR coin flip → schema gate → section/skill/difficulty pin → self-verify → multi-validity check/repair → dedup-hash → per-row insert) and returns the fine-grained `BatchSummary` counters so the cron JSON summary stays byte-equivalent. Because the top-up path can race the hourly n8n generator, the insert's `error.code === '23505'` branch (count as `rejectedDuplicate`, keep going) must stay — a duplicate must be **counted, not thrown**. The top-up path calls it with **no difficulty argument → the default `'medium'`** (difficulty-targeted top-up is explicitly deferred); `runGeneration` always pins the thinnest cell's difficulty. `topupSkill` reads `batch.accepted` as its `inserted` count.
- **Cooldowns (`GUIDANCE_COOLDOWN_MIN` = 10, `TOPUP_COOLDOWN_MIN` = 30, in `app/lib/practice/generation.ts`) are BEST-EFFORT under concurrency.** They are checked by reading a timestamp (`skill_guidance.generated_at` / the latest `practice_topups` row) — serverless has no shared memory, so two near-simultaneous saves can both pass the check and both generate. The harm is bounded: at worst one wasted Ollama batch; dedup (the `23505` catch) converges the rows and the guidance upsert is idempotent on the pk. **Do not add locking** to "fix" this — the cost of a lock exceeds the cost of an occasional wasted batch.
- **Static lessons in `app/lib/lessons/` are now the FALLBACK layer — do NOT delete them.** The skill page renders the AI base lesson row when one exists (`getSkillLessonRow`); otherwise it falls back to the static `getLesson(skill)` (and mounts `LessonGenerating`, which fires `/api/practice/lesson` to generate the AI version for next time). So a static lesson is what a student sees on **first visit** and on the **generation-failure path**. `scripts/check-lessons.ts` still enforces every `SKILLS` skill has a complete static lesson — adding a skill still fails it until a static lesson exists (the three-place change is unchanged). `lessonSchema` (`app/lib/ai/lesson-schema.ts`) governs **BOTH** sources (static and AI): `scripts/check-lesson-schema.ts` parses every static lesson through it as a schema-vs-authoring-bounds drift guard, and the generation module validates AI content through it before storing. **Bylines are deliberately neutral** ("Lesson · updated <date>" for the AI row; none for the static fallback) — they do not advertise AI-vs-static; do not add an "AI-generated" label.
- **The three `/api/practice/{lesson,guidance,topup}` routes are session-gated by middleware — do NOT add them to `PUBLIC_PATHS`.** They are absent from `middleware.ts`'s `PUBLIC_PATHS` on purpose (so the session cookie gates them), and each re-checks the session in-route with `supabase.auth.getUser()` (401 if none) because the generation module performs service-role writes. Each sets `maxDuration = 300` because the Ollama calls run 30–60s (matching the generate-questions route budget). The top-up client fetch uses `keepalive: true`, but that only lets the **browser** send the request during navigation away from the summary — it is the **server** (the route's `maxDuration`) that keeps the generation alive after the client disconnects, not the client. Do not shorten `maxDuration` on the assumption keepalive holds the client open.

## Parity sub-project gotchas

The competitive-parity pack has landed (sub-project #15): official full-test module timing + a mandatory 10-minute break, full-test score-validity guards, per-question timing capture + pacing analytics, math figures, empirical difficulty calibration + admin item stats, an answer eliminator, and "Explain my mistake." - **`SECTION_CONFIG.moduleSeconds` (rw `1920`, math `2100`) is the timing source of truth now; `secsPerQ` is DERIVED, not authored.** `secsPerQ = moduleSeconds / moduleSize` (`1920 / 27 ≈ 71.1`, `2100 / 22 ≈ 95.5`) — it is **fractional** on purpose so full-test modules run the official 32/35-minute budgets while short tests keep working (`Math.round(shortCount × secsPerQ)`). Old clients send neither → both coalesce to null; never gate correctness on them.
- **Figure safety wall: models emit a structured spec, `FigureView` is the ONLY renderer, never model-emitted markup.** A model NEVER emits SVG/HTML — it emits one of 6 schema-validated shapes (`table` / `bar-chart` / `line-graph` / `scatterplot` / `triangle` / `circle`) defined by `figureSchema` in `app/lib/ai/figure-schema.ts` (the discriminated union is the safety wall: it **rejects, never repairs**; a schema-invalid figure rejects the whole candidate). `app/components/FigureView.tsx` is the sole renderer — plain dependency-free SVG/HTML, no hooks, `safeParse`s defensively at the top and renders null on anything malformed (the question stays answerable from text). To pin a question against calibration, **disable it** (pinning is deferred).

- **A mid-break snapshot stores the PRE-advance `secIdx` (the just-finished R&W index).** `resumeFromBreak()` does the `secIdx + 1` advance itself, so storing the post-advance index would double-advance on resume (skip Math's Module 1). When `screen === 'break'`, snapshot the current (pre-advance) section index plus `onBreak`/`breakRemaining`; restore re-enters `'break'` and lets `resumeFromBreak()` do the increment.

- **Recovery write points = ONE throttled effect (2 s) + an unthrottled `visibilitychange→hidden`/`pagehide` flush — and NO write during the Module-2 draw.** The single throttled effect covers all state-commit points (answer change, navigation, mark toggle, pause/resume, break entry); the two event-listener flushes catch the crash-adjacent moments. There is deliberately **no snapshot write inside `performModule2Draw`** — an in-flight draw's `module2ParamsRef` is not serializable state, and the pre-submit snapshot already suffices. Every write is wrapped in try/catch so a quota error silently skips and NEVER breaks the running test. Restore is single-fire (a `restoreCheckedRef` guard, Strict-Mode-safe), sets ALL state in one batch before the timer effect can tick, rehydrates refs (`timesMsRef.current` from the snapshot, `activeQuestionRef.current = null` — the `start()` precedent), and runs BEFORE the resave-on-mount effect so a restored test never collides with a leftover `sat:pending-attempt:v1`.

- **In `finish()` the ordering is CLEAR the in-progress snapshot FIRST, then write the pending-attempt backup.** A crash between finish and save must leave ONLY the finished-attempt backup (`sat:pending-attempt:v1`), never both — the two must never coexist for the same test. - **The admin needs-review queue is COMPUTED, not a lifecycle state machine — no new columns, no draw gating.** `sat.admin_review_queue(p_limit int default 50)` is security DEFINER, `grant execute to service_role` ONLY (never callable by students), read via the service client in `getReviewQueue()` (`app/lib/admin/queries.ts`) and rendered at `/admin/review`. ## Study Planner sub-project gotchas (#18)

The study-planner-and-miss-reason pack has landed (sub-project #18): a student tags **why** they missed a question (six reasons), and a `/plan` page turns diagnosis into a weekly "do this next" schedule. Migration `20260707060000_sat_planner.sql`.

- **`MISS_REASONS` is the single source for the miss-reason enum — the SQL CHECK is the ONE allowed duplicate.** `app/lib/practice/miss-reasons.ts` exports `MISS_REASONS` (`{ value, label, promptPhrase }` per entry) for the six values `concept · careless · time_pressure · misread · setup · vocab`. The zod literal union (`MISS_REASON_VALUES`), the six UI chips (`app/components/MissReasonChips.tsx`), and the guidance prompt phrasing (`app/lib/ai/ollama.ts`'s `MISS_REASON_PHRASE` map) all DERIVE from it. The `miss_reason` CHECK constraint on both response tables (migration) is the only hardcoded duplicate — this is the same 2-place discipline as the `SKILLS` taxonomy gotcha (source-of-truth const + one SQL copy). Update both in the same change or the DB rejects a value the UI can produce.

- **`skill_evidence` was DROP + recreated (not CREATE OR REPLACE) — and a DROP LOSES the ACL, so the recreate MUST re-grant.** The migration adds `miss_reason` to `sat.skill_evidence`'s `RETURNS TABLE`, and Postgres forbids CREATE OR REPLACE from changing a return type. So the migration does `DROP FUNCTION sat.skill_evidence(text,int)` then recreates it — and because a DROP drops the ACL, the recreate MUST re-issue `grant execute ... to authenticated` and keep `security invoker` + `set search_path to ''`. **Precedent to remember:** the ACL-preserving `CREATE OR REPLACE` (e.g. `draw_drill` v2, where re-granting is deliberately omitted) does NOT apply when a signature change forces a DROP+recreate — always re-grant on a DROP. `miss_reason` reads straight off the response row (no new join; the `sat.questions` LEFT join stays).

- **`tag_miss_reason` is a SILENT no-op on a non-matching id — a stale client id must never 500.** `sat.tag_miss_reason(p_origin text, p_response_id uuid, p_reason text)` (security definer, `grant execute to authenticated`) picks the table by `p_origin in ('test','practice')` and UPDATEs guarded `where id = p_response_id and user_id = auth.uid() and is_correct = false`; a non-matching id (wrong owner, correct row, gone) returns `false` (via `FOUND`), never raises. `p_reason = null` clears the tag (re-taggable); a non-null value is validated against the closed set (the column CHECK is the backstop). The chips (`MissReasonChips`) render ONLY on incorrect rows and reconcile optimistic UI against the boolean result. Wired on two surfaces: attempt review (`ReviewItem` on `/dashboard/attempts/[id]`, response ids already selected) and the drill recap (`DrillSummary`, practice response ids fetched after save by `session_id` and mapped by `position`). Post-test results-screen review is EXCLUDED (in-memory questions lack response ids).

- **`miss_reason_mix()` is security INVOKER (the `user_analytics` precedent).** `sat.miss_reason_mix()` returns tagged-incorrect counts grouped by `(skill, miss_reason)` across both response tables, RLS-scoped to the caller (keeps an explicit `auth.uid()` filter as a clarity backstop). `grant execute to authenticated`. Do NOT promote it to definer — it reads only RLS-protected tables. It feeds the planner's reason-aware `why` strings via `getMissReasonMix()` in `app/lib/planner/queries.ts`.

- **The study plan is COMPUTED, and completion is DERIVED from this-week activity — there is NO plan-item storage table.** `sat.study_plans` (`user_id` pk, `target_score` 400–1600, `test_date`, `sessions_per_week` 2–7) stores only the student's TARGETS; writes via the bounds-checked `sat.upsert_study_plan(p_target, p_test_date, p_sessions)` (security definer, sets `user_id := auth.uid()`, `grant execute to authenticated`). The weekly plan itself is recomputed each render and a plan item is "done" when a matching drill/test exists this ISO week — no checkboxes to maintain, can't go stale. Do NOT add a plan-items table.

- **Planner compute (`app/lib/planner/compute.ts`) is PURE — `today` is an input, never `Date.now()` inside.** Exports `buildWeekPlan` / `overdueSkills` / `paceSummary` + `PlannerInputs` / `PlanItem` / `OverdueSkill`. ## Daily test limit

A per-user daily test-submit cap (UTC calendar day), app-wide, in the single-row
`sat.app_config` table (`daily_attempt_limit`, default 5). Admins edit it at
`/admin/settings` (the `setDailyAttemptLimit` server action, service-role write).

- **Enforced in two places, keep them in sync.** `app/lib/config.ts` (`getAttemptUsage`) feeds the Start screen, which hides the Start button at the limit — `useTestSession.sessionCompletions` is added to the server count so the gate stays accurate across tests taken without a page reload. The `sat.save_attempt` RPC re-checks the limit and raises `daily attempt limit reached` as the airtight backstop. If you change what counts as an "attempt", change both.
- **`sat.app_config` is RLS select-only** (`select` policy + grant for `authenticated`, no write policy) — writes go through the service-role client behind `requireAdmin()`, same pattern as the rest of `/admin`.

## Things that will bite you

- **Answer indices are positional, and choices get shuffled.** In `questions.ts`, `answerIndex` is the index into `choices` *as authored*. `buildTest()` rewrites both arrays in sync — never re-order one without the other. SPR rows skip this entirely (`shuffleChoices` is a no-op for `response_format === 'spr'`); they carry empty `choices` and a placeholder `answerIndex = 0` that the runner never reads.
- **Section keys are `'rw'` and `'math'`** (not `'reading'`, not `'reading-writing'`). Adding a third section requires updating `SECTION_CONFIG`, `SECTION_ORDER`, and confirming `BANK` entries use the new key.
- **Explanations render differently depending on source.** `ReviewItem.tsx` branches on `question.source`: seed explanations (hand-authored, trusted) render via `dangerouslySetInnerHTML`; AI explanations render as React-escaped text. See the AI sub-project gotchas for why — do not collapse these back into a single `dangerouslySetInnerHTML`.
- **Timer auto-advances on zero.** The `useEffect` on `[screen, secIdx]` in `useTestSession.ts` is what restarts the interval, and `handleTimeUp` defers `setSecIdx` via `setTimeout(..., 0)` to avoid setState-mid-render. Don't "simplify" that.
- **Scaled score is now a real (per-section) curve, server-trusted.** Per section: a real Digital SAT lookup table (`RW_CURVE` / `MATH_CURVE` in [app/lib/scoring.ts](app/lib/scoring.ts), mirrored by `sat.scale_section`). The composite is the sum. `sat.save_attempt` computes it itself — the client's `scaledScore` is ignored. Short tests project the raw% onto the full-test count, then look up that. Adaptive module-aware scoring is sub-project #11's job, not #10's.
- **`moduleSeconds` is the timing source of truth; `secsPerQ` is derived and fractional.** `SECTION_CONFIG.moduleSeconds` (rw `1920`, math `2100`) seeds full-test module timers; `secsPerQ = moduleSeconds / moduleSize` (fractional) drives short-test budgets and every other timer seed (each `Math.round`ed so `remaining` starts integral). Retune pacing by editing `moduleSeconds` — do NOT set `secsPerQ` to a whole number (that reverts the official 32/35-minute fix). See the Parity sub-project gotchas.
- **`<body>` has `suppressHydrationWarning` set in `app/layout.tsx`** to silence false positives from browser extensions (Grammarly, Dark Reader, password managers) that inject `data-*` attributes into `<body>` after SSR but before React hydrates. The attribute is scoped to `<body>` only — real hydration mismatches anywhere else still surface normally. Do not remove it (you will start seeing the same extension noise) and do not extend it to other elements (real mismatches would hide).

## Adding questions

Append to `BANK` in [app/lib/questions.ts](app/lib/questions.ts). Shape:

```ts
{
  id: 'seed-math-018',  // stable id; `seed-rw-NNN` or `seed-math-NNN`, 1-indexed
  section: 'rw' | 'math',
  skill: 'Linear Equations',
  passage: '…',         // optional, typically rw only
  prompt: '…',
  choices: ['…', '…', '…', '…'],
  answerIndex: 1,       // index into choices, before shuffle (renamed from old `answer`)
  explanation: '…',     // may contain inline HTML (<b>, <i>)
  source: 'seed',
}
```

Quick-mode pulls `shortCount` per section (currently 10). If `BANK` has fewer than `shortCount` in a section, the test silently uses what's there — bump `shortCount` or add questions to keep the experience consistent.

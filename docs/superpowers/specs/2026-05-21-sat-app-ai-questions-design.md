# SAT Prep — AI Question Generation Sub-Project Design

**Date:** 2026-05-21
**Status:** Approved for plan-writing
**Sub-project:** #2 of 7 — AI Question Generation
**Audience:** Future implementer (human or AI) building the question pool
**Builds on:** Foundation (#1, tag `post-foundation`) and Auth (#3, tag `post-auth`)

---

## 1. Context: where this fits

The SAT app currently draws every test from a static, in-code bank: `app/lib/questions.ts` exports `BANK`, 33 hand-written questions (16 Reading & Writing, 17 Math). `buildTest(name, testLength, bank)` shuffles and slices that bank. Every test any user takes is sampled from the same 33 questions — they repeat quickly.

This sub-project replaces the static bank as the *runtime* source with a **growing pool of AI-generated SAT questions** stored in a new `sat.questions` table. Questions are generated by **Ollama Cloud** (a DeepSeek model) behind a pluggable provider interface, quality-gated (schema validation + self-verify), de-duplicated, and topped up on a **schedule** (cron). The in-code `BANK` survives only as the seed content and an offline fallback.

A key product requirement refines the pool model: the pool is **shared** (different users may see overlapping questions), but **a single user must never be re-served a question they have already attempted** — each of their tests pulls fresh material. When a user has worked through everything available, the system **recycles their least-recently-seen questions** rather than blocking or making them wait.

Auth (#3) is already done, so every test belongs to a known `auth.users` id — that identity is what the per-user no-repeat logic keys on.

This sub-project does **not** build persistence of scores/attempt history (that is sub-project #4); it records only the lightweight "which questions has this user been served" data its no-repeat rule needs.

## 2. Scope

### 2.1 In scope

- **`sat.questions`** table — the shared global question pool; seeded from `BANK`.
- **`sat.served_questions`** table — per-user record of which questions each user has been served.
- **`sat.draw_questions(section, count)`** RPC — atomically selects un-served (or recycled least-recently-served) questions for the calling user and records them.
- **`AIProvider` interface** + one adapter, **`OllamaCloudProvider`** (DeepSeek model on Ollama Cloud). A `getProvider()` factory keyed on `SAT_AI_PROVIDER`.
- **Generation endpoint** — a secret-protected route handler that checks pool depth per `(section, skill)`, generates a bounded batch via the provider, runs each candidate through the quality gate (zod schema validation → self-verify → dedup), and inserts survivors.
- **Vercel Cron** config that calls the generation endpoint on a schedule; the endpoint is also manually triggerable for local dev.
- **Seed step** — idempotently upserts the 33 `BANK` entries into `sat.questions`.
- **Gameplay wiring** — `useTestSession.start()` becomes async: it draws questions from the pool via the RPC and feeds them into the existing `buildTest(...)` seam, with a loading state and a `BANK` fallback.
- **`fullCount`** added to `SECTION_CONFIG` so a "Full" test has a defined size against a large pool.
- **Safe rendering of AI explanations** — closes the XSS risk Foundation explicitly deferred to this sub-project (`dangerouslySetInnerHTML` in `ReviewItem`).
- New env vars + a service-role Supabase client (server-only).
- Docs sync + a `post-ai` git tag.

### 2.2 Out of scope (explicitly deferred)

- **Difficulty levels / adaptive testing.** The `Question` type has no difficulty field; none is added.
- **Other provider adapters** (OpenAI, Claude, local Ollama). The `AIProvider` interface is built so they are pure additions later; they are not implemented now.
- **Persistence of scores / attempt history / per-question responses** — sub-project #4. This sub-project records only `served_questions` (no scores, no chosen answers).
- **Question editing / rating / regeneration UI**, admin moderation of the pool.
- **Per-user *pools*** — the pool is one shared global set; only the *exclusion* is per-user.
- **Automated test suites** — verification is `pnpm type-check` + `pnpm lint` + `pnpm build` + scripted/manual checks (matches Foundation Decision D8).

### 2.3 Acceptance criteria

1. `pnpm install`, `pnpm dev`, `pnpm build`, `pnpm type-check`, `pnpm lint` all succeed.
2. `sat.questions` and `sat.served_questions` exist with RLS enabled; `sat.questions` holds the 33 seed rows after seeding.
3. The generation endpoint, given a valid secret, generates questions, rejects schema-invalid / self-verify-failing / duplicate candidates, and inserts the survivors.
4. Calling the endpoint without the secret is rejected.
5. `sat.draw_questions` returns `count` questions for the calling user, never including one already in that user's `served_questions` until the un-served supply for that section is exhausted, after which it recycles least-recently-served — and it records every drawn question.
6. Starting a test pulls from the pool; a user taking two tests in a row does not see a repeated question while fresh ones remain.
7. If the pool draw fails, the test still builds from the in-code `BANK`.
8. AI-generated explanations render without an HTML-injection vector.
9. A "Full" test has a bounded size (`fullCount`), not "every question in the pool".

## 3. Architecture decisions (locked)

Made through brainstorming with the stakeholder on 2026-05-21.

| # | Decision | Rationale |
|---|---|---|
| G1 | **Ollama Cloud (a DeepSeek model) is the one implemented provider**, behind a pluggable `AIProvider` interface. OpenAI/Claude/local-Ollama adapters are *not* built. | Foundation's notes listed four adapters; building three unused ones is over-engineering (YAGNI). The interface is the real value — it keeps adding a provider a small isolated task. Ollama Cloud + DeepSeek is the stakeholder's chosen provider. |
| G2 | **The pool is topped up by a scheduled cron**, not by a fire-and-forget job at test start. | Background work on serverless (Vercel) is fragile — the function can be frozen once the HTTP response is sent, mid-batch. A cron decouples generation from gameplay: users never wait, and reliability does not depend on serverless background execution. |
| G3 | **The pool is shared/global; the no-repeat rule is per-user.** Different users may see overlapping questions; a single user is never re-served a question they have already been served, tracked in `sat.served_questions`. | Stakeholder requirement. A shared pool keeps generation economical (one pool serves everyone); per-user exclusion gives each user a fresh experience. |
| G4 | **Recording is at *serve* time**, not submit time: when `draw_questions` hands a question to a user it is immediately recorded as served. | Submit-time recording would require the attempt-persistence machinery of sub-project #4. Serve-time recording is self-contained, and it errs toward *not* repeating (a started-then-abandoned test "uses up" its questions) — acceptable, and the recycle rule (G5) keeps it from ever blocking. |
| G5 | **On exhaustion, recycle least-recently-served.** When a user has no un-served questions left for a section, `draw_questions` fills the test with that user's oldest-served questions and refreshes their `served_at`. | A finite pool plus a fast repeat user makes strict-no-repeat + never-wait + never-blocked impossible simultaneously. Recycling never blocks and never waits; the cron keeps the pool growing so genuine repeats stay rare. |
| G6 | **Quality gate = zod schema validation → self-verify → dedup.** Self-verify: the provider re-solves its own generated question; if its answer index ≠ the stated `answerIndex`, the question is rejected. Dedup: a normalized hash of `prompt`+`choices`, enforced by a `UNIQUE` constraint. | Foundation pre-decision. Catches malformed output and internally-inconsistent questions cheaply. It does not catch a "well-formed but pedagogically poor" question — accepted limitation for v1. |
| G7 | **AI-generated explanations are rendered as plain (React-escaped) text; only `source='seed'` explanations keep `dangerouslySetInnerHTML`.** | Foundation flagged the `dangerouslySetInnerHTML` in `ReviewItem` as a real XSS risk "once questions become AI-generated" and deferred the fix here. AI output is untrusted; rendering it through React's normal escaping is definitively safe and needs no sanitizer dependency. Seed content is hand-authored and trusted. The existing `Question.source` field is the discriminator. |
| G8 | **The in-code `BANK` becomes seed + fallback only.** It seeds `sat.questions` once; at runtime it is used only if the pool draw fails. | Keeps gameplay resilient to a DB/provider outage and keeps question content single-sourced for the seed. |
| G9 | **No automated tests** (matches Foundation D8). Verification is type-check + lint + build + a scripted end-to-end check + manual review. | Project convention. |

## 6. Data model

### 6.1 Migration — `supabase/migrations/20260521030000_sat_questions.sql`

```sql
-- AI sub-project — question pool + per-user serve history + the draw RPC.

-- ---- sat.questions: the shared global pool --------------------------------
create table if not exists sat.questions (
  id            text primary key,                      -- 'seed-rw-NNN' | 'ai-<uuid>'
  section       text not null check (section in ('rw','math')),
  skill         text not null,
  passage       text,
  prompt        text not null,
  choices       jsonb not null,                        -- string[]
  answer_index  int  not null,
  explanation   text not null,
  source        text not null default 'ai' check (source in ('seed','ai')),
  dedup_hash    text not null unique,                  -- normalized hash of prompt+choices
  created_at    timestamptz not null default now()
);
create index if not exists questions_section_idx on sat.questions (section);

alter table sat.questions enable row level security;

-- Read-only to authenticated users; the whole pool is readable (it is shared).
-- There is intentionally NO insert/update/delete policy: even though Supabase
-- grants table privileges to `authenticated` on exposed-schema tables, RLS with
-- no write policy denies all writes. The generation endpoint writes via the
-- service role, which bypasses RLS.
create policy "questions_select" on sat.questions
  for select to authenticated using (true);

-- ---- sat.served_questions: per-user serve history ------------------------
create table if not exists sat.served_questions (
  user_id      uuid not null references auth.users (id)   on delete cascade,
  question_id  text not null references sat.questions (id) on delete cascade,
  served_at    timestamptz not null default now(),
  primary key (user_id, question_id)
);
create index if not exists served_user_section_idx
  on sat.served_questions (user_id, served_at);

alter table sat.served_questions enable row level security;

-- A user may read only their own serve history. Writes happen only inside the
-- draw_questions RPC (security definer → bypasses RLS), so no write policy.
create policy "served_select_own" on sat.served_questions
  for select to authenticated using ((select auth.uid()) = user_id);

-- ---- sat.draw_questions: atomic per-user test draw -----------------------
-- Returns `p_count` questions for the calling user in section `p_section`:
--  1. random questions the user has NOT been served, then
--  2. if short, the user's least-recently-served questions for that section.
-- Every returned question is recorded/refreshed in served_questions.
create or replace function sat.draw_questions(p_section text, p_count int)
returns setof sat.questions
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_user  uuid := (select auth.uid());
  v_count int  := least(greatest(coalesce(p_count, 0), 0), 60);  -- bound the request
  v_ids   text[];
begin
  if v_user is null then
    raise exception 'not authenticated';
  end if;

  -- 1. fresh, un-served
  select coalesce(array_agg(id), array[]::text[]) into v_ids from (
    select q.id from sat.questions q
    where q.section = p_section
      and not exists (
        select 1 from sat.served_questions s
        where s.user_id = v_user and s.question_id = q.id)
    order by random()
    limit v_count
  ) fresh;

  -- 2. recycle least-recently-served if short
  if coalesce(array_length(v_ids, 1), 0) < v_count then
    select v_ids || coalesce(array_agg(id), array[]::text[]) into v_ids from (
      select q.id
      from sat.questions q
      join sat.served_questions s
        on s.question_id = q.id and s.user_id = v_user
      where q.section = p_section
        and not (q.id = any(v_ids))
      order by s.served_at asc
      limit v_count - coalesce(array_length(v_ids, 1), 0)
    ) recycled;
  end if;

  -- 3. record / refresh serve history
  insert into sat.served_questions (user_id, question_id, served_at)
  select v_user, unnest(v_ids), now()
  on conflict (user_id, question_id) do update set served_at = excluded.served_at;

  -- 4. return the drawn questions
  return query select * from sat.questions q where q.id = any(v_ids);
end;
$$;

grant execute on function sat.draw_questions(text, int) to authenticated;
```

Notes:
- `draw_questions` is `security definer` so it can write `sat.served_questions` and read the whole pool; it scopes everything to `auth.uid()`. `p_count` is bounded (≤ 60) so a malicious caller cannot draw or record an unbounded number of rows.
- The migration is applied by the **controller** via `mcp__claude_ai_Supabase__apply_migration` (the implementer writes and commits the file).

### 6.2 Row ↔ `Question` mapping

`sat.questions` rows use snake_case (`answer_index`) and carry `dedup_hash`/`created_at`. A small `rowToQuestion()` mapper produces the existing `Question` type (`id, section, skill, passage?, prompt, choices, answerIndex, explanation, source`). The `Question` interface in `app/lib/questions.ts` is unchanged.

## 7. Provider and generation pipeline

### 7.1 `AIProvider` interface (`app/lib/ai/provider.ts`)

```ts
export interface GeneratedQuestion {
  section: 'rw' | 'math';
  skill: string;
  passage?: string;
  prompt: string;
  choices: string[];
  answerIndex: number;
  explanation: string;
}

export interface AIProvider {
  // Generate `count` fresh questions for one (section, skill).
  generateQuestions(section: 'rw' | 'math', skill: string, count: number): Promise<GeneratedQuestion[]>;
  // Re-solve a question; returns the chosen choice index. Used by the self-verify gate.
  solve(q: Pick<GeneratedQuestion, 'section' | 'skill' | 'passage' | 'prompt' | 'choices'>): Promise<number>;
}

export function getProvider(): AIProvider; // reads SAT_AI_PROVIDER; throws on unknown
```

### 7.2 `OllamaCloudProvider` (`app/lib/ai/ollama.ts`)

Calls Ollama Cloud's chat API with the model from `SAT_AI_MODEL`, authenticated with `OLLAMA_API_KEY`. `generateQuestions` prompts for `count` SAT-style questions for the given section+skill as **strict JSON** (and asks for **plain-text explanations**, no HTML). `solve` sends a question and asks only for the chosen index. Exact endpoint URL and model tag are confirmed against Ollama Cloud's API at implementation time and pinned in the plan.

### 7.3 Quality gate (`app/lib/ai/schema.ts`, `app/lib/ai/dedup.ts`, `app/lib/ai/generate.ts`)

For each generated candidate, in order:
1. **Schema** — a zod schema validates shape: non-empty `prompt`, `choices` of length 4, integer `answerIndex` in `0..choices.length-1`, non-empty `explanation`, `section`/`skill` valid. Invalid → reject.
2. **Self-verify** — `provider.solve(candidate)`; if the returned index ≠ `candidate.answerIndex`, reject (the model contradicts itself). `solve` is a fresh call given only the question (its `Pick` type excludes `answerIndex` and `explanation`) so the model genuinely re-solves rather than echoing a stated answer.
3. **Dedup** — `dedupHash(prompt, choices)` = a SHA-256 of the normalized text (`toLowerCase`, whitespace-stripped, choice-order-preserving, joined with a separator). Insert with `on conflict (dedup_hash) do nothing`; a conflict means a duplicate and is counted as rejected.

Survivors are inserted into `sat.questions` with `id = 'ai-' + crypto.randomUUID()`, `source='ai'`.

### 7.4 Generation endpoint (`app/api/admin/generate-questions/route.ts`)

A `GET` route handler (Vercel Cron issues `GET`). It rejects any request whose `Authorization` header is not `Bearer ${CRON_SECRET}`. On success it:
1. Computes pool depth per `(section, skill)` over the `SKILLS` taxonomy.
2. Picks the most-depleted skill(s), bounded so total generation per invocation stays within the serverless function timeout. **Concrete default:** at most ~3 questions per skill and at most 2 skills per invocation (≤ ~6 candidates/run); the cron runs often enough to grow the pool steadily. Tunable via constants in `generate.ts`.
3. Runs the §7.3 pipeline.
4. Returns a JSON summary: `{ generated, accepted, rejectedSchema, rejectedSelfVerify, rejectedDuplicate }`.

All DB access here uses the **service-role client** (`app/lib/supabase/admin.ts`).

The `SKILLS` taxonomy (a constant in `app/lib/questions.ts`) lists the skills per section; it is seeded from the distinct skills present in the current `BANK` and is the set the generator targets.

## 8. Gameplay integration

`SECTION_CONFIG` gains `fullCount` (`rw: 27`, `math: 22` — a realistic module-pair; tunable). `buildTest` and its `bank` parameter are unchanged — it remains the seam. For a Full test the caller draws exactly `fullCount` questions per section and passes only that slice as `bank`; `buildTest`'s `testLength === 'full'` branch then takes `pool.length` (= `fullCount`). The `StartScreen` "Full" option label is updated from "all questions" to the bounded size (e.g. "Full (27 + 22)"), since "all questions" is no longer accurate against a large pool.

`useTestSession`:
- `start()` becomes **async**. For each section it calls the `draw_questions` RPC (via the browser Supabase client) for `shortCount` (Quick) or `fullCount` (Full) questions, maps the rows to `Question[]`, concatenates, and calls `buildTest(name, testLength, drawn)`.
- A new `loading: boolean` field is added to the `TestSession` interface; `start()` sets it while drawing.
- **Fallback:** any failure (RPC error, network, empty result) → `buildTest(name, testLength)` with the in-code `BANK`. The user always gets a test.

`StartScreen` reads `loading` and, while true, disables the Start button and shows "Building your test…".

Because `draw_questions` records served questions, a returning user's next test automatically excludes everything they have seen, until the recycle path (G5) engages.

## 9. Security: AI explanation rendering

Foundation's risk table explicitly deferred this: `ReviewItem` renders `question.explanation` with `dangerouslySetInnerHTML` because seed explanations contain trusted `<b>` tags — and flagged that once explanations are AI-generated this is an XSS vector.

Fix (Decision G7): `ReviewItem` branches on `question.source`:
- `source === 'seed'` → keep `dangerouslySetInnerHTML` (hand-authored, trusted).
- otherwise (`'ai'`) → render `explanation` as ordinary React text, which React escapes — no injection is possible.

The Ollama prompt also asks for plain-text explanations, so AI explanations have no formatting to lose. This needs no sanitizer dependency.

## 11. Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Generated questions are well-formed but pedagogically weak or subtly wrong in a way self-verify misses (the model agrees with its own bad answer). | Medium | Medium | Accepted limitation for v1 (G6). Self-verify catches internal inconsistency; zod catches malformed shape. A future sub-project can add human review or a second-model check. Documented. |
| Serverless function timeout during a generation batch. | Medium | Low | Batches are small and bounded per invocation (§7.4); the cron runs often enough to keep the pool growing. |
| `SUPABASE_SERVICE_ROLE_KEY` leaked to the client. | Low | High | The key lives only in `app/lib/supabase/admin.ts`, imported only by server-only modules (the generation endpoint, the seed script). It is never `NEXT_PUBLIC_`-prefixed. A grep check is part of verification. |
| AI explanation XSS. | — | High if unaddressed | Closed by G7 / §9 — AI explanations are React-escaped, never `dangerouslySetInnerHTML`. |
| `draw_questions` abused with a huge `p_count`. | Low | Low | `p_count` is clamped to ≤ 60 inside the RPC. |
| Pool exhaustion for an active user. | Medium | Low | Recycle path (G5) — never blocks; the cron keeps the pool growing. |
| Ollama Cloud / DeepSeek API shape differs from assumptions. | Medium | Low | The provider is isolated behind `AIProvider`; the exact endpoint/model is confirmed at implementation and pinned in the plan. Only `ollama.ts` would change. |
| Migration touches the shared Property Ledger DB. | Low | Medium | Additive, confined to the `sat` schema (two tables, one function). Applied + verified via MCP, as Foundation/Auth migrations were. |
